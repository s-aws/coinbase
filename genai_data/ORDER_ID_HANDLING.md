# Order ID Handling

## Critical Rule

Use `client_order_id` for internal tracking.
Use `order_id` only when interacting with exchange APIs or exchange-origin identifiers.

If you mix them, you get phantom parents, failed lookups, missed-fill noise, and bad reconciliation.

## ID Types in This Repo

### 1) `client_order_id` (internal primary identifier)

Source:
- Generated by this system (UUID strings). New `order_parent` inserts reject non-UUID `client_order_id` / `parent_order_id` values before hitting the database.

Used for:
- `order_parent.client_order_id` and parent-child linkage (`parent_order_id`).
- in-memory orderbook keys (`OrderBook._orders`, parent/child maps).
- follow-up claims and replacement-slot accounting.
- partial-fill progress (`partial_fill_progress.client_order_id`).
- fill-ledger derived key lineage (`FillLedger.client_order_id`).
- dashboard-level order references.

### 2) `order_id` (exchange-assigned identifier)

Source:
- Coinbase order placement responses and user channel payloads.

Used for:
- exchange queries/cancel/reporting
- mapping exchange events back to internal orders when needed
- reconciliation and forensic evidence

Never use `order_id` as the canonical in-memory or DB parent key.

## Canonical Mapping Strategy

When exchange data must be joined back to local ownership:
- map `order_id -> client_order_id` through submission evidence in `order_event_stream`
- filter to rows where:
  - `event_type = order_submitted`
  - `source_channel = rest_submit`

Reason:
- shared-account websocket streams can include orders not owned by this engine instance.
- ownership must be anchored on our own submission evidence.

## Stealth-Specific ID Rules

- Root stealth order id is also the root `client_order_id` for hierarchy purposes.
- Revealed placements can mint fresh placement `client_order_id` values.
- Exchange `order_id` for revealed placement is supplemental and may arrive later.
- Move-revealed keeps the same stealth root but replaces placement identifiers.
- Cancel/re-entry keeps the same stealth root, cancels the active placement, stores the cancelled placement identifiers in `cancel_reentry_state_json`, and later re-enters with a new placement identifier through the normal reveal path.
- Exchange cancellation uses the exchange-facing order identifier required by Coinbase, usually the tracked `active_exchange_order_id`. Local linkage, parent rows, dashboard references, and follow-up ownership still use `client_order_id`.

Related code:
- `core/stealth_order_manager.py`
- `bridges/stealth_order_bridge.py`
- `database/order.py::stealth_order_moves`

## Fill and Reconciliation IDs

The fill pipeline uses three identifier classes:

1. `derived_trade_key`
- deterministic UUID5 from `(client_order_id, cumulative_quantity)`.
- idempotency key for WS-derived fill rows.

2. `exchange_trade_id` / `exchange_entry_id`
- authoritative IDs from REST historical fills.
- stamped during reconciliation (`RECONCILED`).

3. `order_id`
- exchange order reference used to fetch historical fills and map ownership.

Do not replace `derived_trade_key` with exchange ids in live WS ingestion path.
That would break idempotency and reprocessing safety.

## Parent/Child Lineage Contract

- Parent and child lineage is always keyed by `client_order_id`.
- Child `parent_order_id` points to original root parent `client_order_id`.
- Never reparent children to children.
- Test-shaped strings such as `test_order_6` are invalid parent identifiers. They can break UUID-typed joins, so inserts are guarded and reconciliation skips any legacy polluted non-UUID parent row instead of aborting the reconcile pass.

## Common Mistakes to Avoid

- Using `order_id` as `order_parent.client_order_id`.
- Looking up internal parent links by `order_id`.
- Treating shared-account websocket `order_id` as proof of local ownership.
- Writing alternate helper paths that sometimes use `client_order_id` and sometimes `order_id` for the same behavior.
- Inserting human-readable test IDs into production-like databases.

## Quick Decision Table

- Need internal lookup, cache key, parent linkage, follow-up tracking?
  - Use `client_order_id`.

- Need to call exchange endpoint, cancel, or inspect exchange-native payload?
  - Use `order_id` (or whichever exchange field is explicitly required).

- Need to mutate a revealed stealth placement locally after an exchange cancel/move?
  - Use `client_order_id` for local lookup and parent linkage, and the tracked exchange order id only for the Coinbase cancel call.

- Need to partition owned vs unowned exchange fills/orders?
  - Use `order_event_stream` submission evidence to resolve `order_id -> client_order_id` first.
